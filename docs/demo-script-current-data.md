## 二、视频主线和镜头原则

这条视频只讲一件事：**一笔经销商佣金少记后，RevGuard 如何从工单开始，复算出正确金额，等待人工批准，执行受控入账，再在独立验证发现偏差后自动回滚。**

每一个自动化步骤都用同一套表达方式：

> **Worker 是谁 → 调用了哪个 Skill → Skill 产生了什么结果 → WebUI 哪个阶段和哪条记录发生了变化。**

镜头保持右侧“多智能体协同任务账本”和左侧业务记录之间的对应关系。左侧不是模型聊天内容，而是已经持久化的业务证据、计算结果和审计事件；只有阶段结果成功保存，流程状态才会进入下一步。

## 00:00–01:20｜场景引入：经销回款佣金模式是什么

### 00:00–00:10｜先给出真实业务场景

**画面：** 黑底标题，随后进入 RevGuard 案件工作台。字幕：`经销商佣金结算：销售、回款、政策与台账`。

**旁白：**

> 在很多企业里，产品不是只通过直营团队销售，还会通过经销商或渠道代理商销售。经销商完成销售后，企业要根据合同和佣金政策，计算应该支付给经销商的佣金；客户实际付款后，还可能产生一笔与回款相关的佣金。

### 00:10–00:45｜用一条业务链解释模式

**画面：** 用简单流程字幕表现：`经销商完成销售 → 客户向企业付款 → 企业读取政策和合同 → 计算佣金 → 记入佣金台账 → 对账或发放`。

**旁白：**

> 这里有两个容易混淆的金额。第一，订单金额，是客户这笔业务的交易金额；第二，佣金，是企业按照政策计算后应当结算给经销商的钱。客户的回款是客户支付给企业的金额，它本身不是经销商的佣金；回款佣金则是满足条件后，按照回款金额和政策比例计算出的佣金组成部分。
>
> 例如，一笔订单金额为一十八万 KES，客户在规定期限内完成同额回款。若政策规定销售佣金按百分之十五、回款佣金按回款金额的百分之三计算，那么销售佣金是二万七千 KES，回款佣金是五千四百 KES，两项合计三万二千四百 KES。这里的 KES 是肯尼亚先令。

### 00:45–01:05｜一次解释六个名词

**画面：** 依次显示名词和一句话定义，保持每个词至少停留 2 秒。

| 名词 | 视频中的一句话解释 |
|---|---|
| 经销商 | 代表企业销售产品或服务、并按约定获得佣金的渠道合作方。 |
| 回款 | 客户向企业实际支付并被财务系统确认的款项，不等于佣金。 |
| 佣金 | 企业依据销售、回款等规则，最终应结算给经销商的金额。 |
| 政策 | 规定佣金比例、适用条件、生效时间和计算方式的一组业务规则。 |
| 等级 | 经销商在特定业务时点对应的级别，例如 GOLD、SILVER 或 BRONZE。 |
| 工单 | 记录佣金异议、差异或处理请求，并作为系统启动调查的入口。 |

**旁白：**

> 这六个词分别对应业务主体、资金事实、应付结果、规则来源、适用身份和处理入口。系统必须把它们绑定到同一个案件，才有可能复算出可以审计的结果。

### 01:05–01:20｜说明为什么会算错，并引出 RG

**画面：** 字幕依次出现：`政策版本错用`、`等级时点错位`、`回款佣金漏记`、`重复入账`、`人工批处理不可追溯`。

**旁白：**

> 现实中，佣金并不只是把订单金额乘一个比例。政策会按季度变化，等级会在不同日期生效，回款、退款和台账还来自不同系统。人工处理很容易错用旧政策、漏掉回款佣金，或者重复写入台账。
>
> RevGuard 的作用，是把工单变成可追溯的案件：先采集证据，再按业务时点选政策，用确定性规则重新计算，经过风险分级和人工审批后才允许写入；写入后由不同主体独立验证，验证失败就反向冲销，并确认恢复到执行前状态。

## 01:20–01:45｜Case8：先读懂这几个金额

**画面：** 选择 `CASE-2026-0008`，等待案件摘要和流水线加载完成。镜头先停留在顶部金额卡片，再移动到“计算账本”。不要在旁白中把订单金额读成应付金额。

| WebUI 字段 | Case8 数值 | 正确读法和含义 |
|---|---:|---|
| 订单金额 | `180,000.00 KES` | 十八万肯尼亚先令；表示订单交易金额，不表示给代理商的佣金。 |
| 已入账金额 | `18,000.00 KES` | 一万八千肯尼亚先令；表示当前佣金台账已经记入的累计金额。 |
| 预期佣金（正确） | `32,400.00 KES` | 三万二千四百肯尼亚先令；表示系统按有效政策复算出的累计应有佣金。 |
| 本次审批金额 | `14,400.00 KES` | 一万四千四百肯尼亚先令；表示本次允许调整的额度，不表示已经完成银行回款。 |

**旁白：**

> Case8 的订单金额是十八万 KES，当前台账已入账一万八千 KES。系统按订单日期匹配到 `2026-Q3` 政策后，复算出的正确累计佣金是三万二千四百 KES。因此，本次需要补记的调整额是三万二千四百减去一万八千，也就是一万四千四百 KES。
>
> 这里订单金额、预期佣金和本次审批金额不相等是正常的。订单金额描述业务规模，预期佣金描述累计应有结果，本次审批金额描述本次要改动的差额；真正写入台账的是按组件拆开的调整记录，而不是把订单金额直接付给经销商。

### 金额相同或不同时，系统怎么处理

**画面：** 可在标题卡或结尾用 10 秒显示以下规则；主线不切换其他案件。

| 比较关系 | 系统含义 | 执行结果 |
|---|---|---|
| 预期佣金 = 已入账金额 | 台账已经与复算结果一致，没有差额。 | 归为无需调整的只读结果，不创建审批，不写入台账。 |
| 预期佣金 > 已入账金额 | 少记佣金，需要补记正向差额。 | 根据风险等级生成审批或草稿；Case8 属于 L2，批准后才可写入。 |
| 预期佣金 < 已入账金额 | 多记佣金，需要扣回或冲销负向差额。 | 不允许无审批自动扣回，必须走更严格的人工审批和受控冲销。 |
| 审批额度与执行草稿不匹配 | 当前动作超出案件、币种、组件或额度边界。 | 权限或台账接口拒绝执行，不静默放大或改写审批范围。 |

在 Case8 中，`14,400.00 KES` 与两项正向差额之和一致：销售佣金补记 `9,000.00 KES`，回款佣金补记 `5,400.00 KES`。这表示本案可以按完整审批范围执行；它仍然不等于已经付款给经销商。

## 01:45–03:35｜逐步执行：每一步都是 Worker 调用 Skill

### 01:45–01:55｜总览：编排器派发阶段任务

**画面：** 展开右侧“多智能体协同任务账本”，显示 `revguard-orchestrator`、AgentTeams Matrix 和当前阶段；不要把编排器说成实际审批人或记账人。

**旁白：**

> 现在进入 Case8 的执行链。编排器只负责按照状态机派发任务和接收阶段结果，具体工作由不同 Worker 完成。每个 Worker 只能看到与自身角色匹配的 Skill；它不能越权调用写台账或审批接口。

### 01:55–02:05｜Worker 1：整理案件并匹配实体

**画面：** 右侧展开第一条任务，保留任务输入、任务输出、执行者、Skill、请求 ID 和回执 ID；再回到左侧审计详情，显示案件创建和阶段变化。

**任务对应：** `revguard-intake` → `CaseNormalizeSkill`；随后同一 Worker → `EntityResolveSkill`。

**旁白：**

> 受理 Worker 先把工单整理成标准案件，确认案件类型是佣金少记，并绑定订单、代理商和币种；随后解析为系统中的唯一代理商实体。左侧新增的案件事件说明“案件已经被系统接收”，右侧任务账本则记录这次调用的输入、输出和执行者。这里记录的是可复核的阶段结果，不是模型自由生成的一段总结。

### 02:05–02:20｜Worker 2：跨系统采集证据

**画面：** 展开 `revguard-evidence` 任务；展示 CRM、合同、财务和政策来源的 8 条证据、工具回执及 `STRONG` 强度。镜头回到左侧“证据来源链”。

**任务对应：** `revguard-evidence` → `EvidenceCollectSkill`。

**旁白：**

> 取证 Worker 只读访问订单、代理商等级历史、合同、回款、退款、发票、佣金台账和政策版本，形成八条带来源和回执的证据。左侧“证据来源链”每一行对应一个来源事实；它告诉我们数据从哪里来、是否校验过，而不是把不同系统的金额拼在一起。

### 02:20–02:35｜Worker 3：按业务时点选择政策

**画面：** 展示右侧“政策时间线”：`2026-Q1`、`2026-Q2` 被排除，`2026-Q3` 被选中；字幕标出业务日期 `2026-07-10` 和等级 `GOLD`。

**任务对应：** `revguard-policy` → `PolicyVersionMatchSkill`。

**旁白：**

> 政策 Worker 不按今天的日期，也不按工单提交日期计算，而是用订单发生日期回溯有效政策。Case8 的业务日期是二零二六年七月十日，因此选择 `2026-Q3`；同时读取该时点的 GOLD 等级。这个步骤解决的是“到底应该用哪一版规则”，不是直接计算金额。

### 02:35–02:55｜Worker 4：用确定性规则复算佣金

**画面：** 右侧展开 `revguard-calculation` 的任务输入和输出；左侧“计算账本”出现逐项公式和代入值。

**任务对应：** `revguard-calculation` → `CommissionCalculateSkill`。

**旁白：**

> 计算 Worker 把已确认的订单金额、回款金额、付款天数、政策版本和等级交给确定性规则引擎。销售佣金是 `180,000 × 15% = 27,000 KES`；回款在订单完成后十六天到账，满足三十天条件，所以回款佣金是 `180,000 × 3% = 5,400 KES`；合计 `32,400 KES`。
>
> 这里的回款佣金公式使用回款金额。Case8 中订单金额和回款金额恰好相同，所以结果看起来都是以十八万为基数；在真实案件中，两者不一定相同。

### 02:55–03:10｜Worker 5：逐组件解释差异

**画面：** 展示左侧“计算账本”的“应有金额 / 已发布 / 差异”三列，以及右侧 `revguard-rootcause` 任务输出中的根因和说明。

**任务对应：** `revguard-rootcause` → `DifferenceExplainSkill`。

**旁白：**

> 根因 Worker 逐项比较“应有”和“已记”。销售佣金应有二万七千、已记一万八千，少记九千；回款佣金应有五千四百、台账中没有这项，少记五千四百。系统把差异归因为政策版本使用错误和回款组件缺失，合计需要补记一万四千四百 KES。

### 03:10–03:35｜Worker 6：风险分级并创建审批

**画面：** 右侧展开 `revguard-risk` 的任务；先显示 `RiskClassifySkill` 输出 `L2`，再显示 `ApprovalRouteSkill` 创建审批单。顶部流水线停在 `WAITING_FOR_APPROVAL`。

**任务对应：** `revguard-risk` → `RiskClassifySkill`；同一 Worker → `ApprovalRouteSkill`。

**旁白：**

> 风险 Worker 根据调整方向、额度、证据完整度和政策冲突判断风险。本案证据充分、金额在 L2 范围内，但属于真实台账写入，所以需要财务负责人审批。系统创建的审批额度是两项组件差额的绝对值之和，也就是九千加五千四百，合计一万四千四百 KES。
>
> 到这里系统会停下来，不会因为计算完成就自动写账。左侧审计详情记录风险判定和审批创建，右侧任务账本记录调用回执，流水线停在等待审批，等待真实的人类决定。

## 03:35–04:15｜人工审批：把“算对”与“允许执行”分开

**画面：** 保持 Case8 不切换案件。展示顶部 `WAITING_FOR_APPROVAL`、`本次审批金额 14,400.00 KES`，进入审批弹窗，再切到“权限边界”查看案件、币种、组件额度、审批角色和身份指纹。登录过程暂停录制或遮挡密码。

**操作要求：** 由组员本人使用 AgentTeams `admin` 完成身份验证并点击“批准”；不要代录、不要显示密码、不要把审批按钮点击前的状态剪成已批准。

**旁白：**

> 现在可以看到，计算结果已经产生，但状态仍然是等待审批。审批金额一万四千四百 KES 是本次调整的授权上限，不是已经支付给经销商的金额；它也不等于订单金额十八万 KES。
>
> 我用实际的人类审批账号完成身份验证并批准这张审批单。后端会把案件、审批单、币种、总额度和两个佣金组件绑定起来，同时留下审批人、认证方式和动作证明。批准后，系统才签发一枚短时、限案件、限币种、限组件额度的执行能力；有效期为十五分钟。
>
> 如果审批被驳回，案件不会写入台账；如果执行草稿超过额度，或者案件、币种、组件与审批凭证不一致，受控接口会拒绝执行。审批本身不是给 Worker 无限写账权限。

**录制验收：** 必须拍到 `APPROVAL_DECIDED` 审计事件、审批人身份和批准后的执行权限；如果实际只停留在待审批，旁白只能说“等待审批”，不能说“已批准”或“已执行”。

**旁白：**

> 这是 demo 中的模拟佣金台账写入，不代表已经从银行账户完成付款；真实支付仍需由企业自己的结算系统按其流程执行。原始记录不会被覆盖，后续如果发生问题，会新增反向冲销记录。

## 04:55–05:35｜独立验证：故障发生时不把错误当成功

### 04:55–05:15｜Worker 9：不同主体重新读取结果

**画面：** 展示 `revguard-verifier` 的任务和 `PostActionVerifySkill` 输出；不要只拍执行 Worker 的成功回执。验证结果显示预期 `32,400.00 KES`、实际读数 `32,401.00 KES`、差异 `1.00 KES`。

**任务对应：** `revguard-verifier` → `PostActionVerifySkill`。

**旁白：**

> 执行成功不代表流程成功。验证 Worker 使用独立身份重新读取佣金台账，不复用执行 Worker 的回执。本次录制在验证读数中模拟增加一 KES，因此系统读到三万二千四百零一 KES，而预期仍是三万二千四百 KES。
>
> 这不是把一 KES 忽略掉的四舍五入问题，而是一个非零差异。验证 Skill 将状态标记为失败，并把 `rollback_required` 置为真。左侧审计详情会留下带错误标识的 `VERIFIED` 事件，右侧任务账本会同时保留验证输入、实际读数和差异原因。

### 05:15–05:35｜说明为什么验证者必须独立

**画面：** 切到“执行与审计”页，展示 AGENT、SKILL、TOOL 类型记录，突出执行者与验证者不同；再回到流水线的 `ROLLBACK_REQUIRED`。

**旁白：**

> 如果执行者自己报告“写入成功”，它只能证明自己调用成功，不能证明源台账最终正确。RevGuard 把执行、验证和回滚拆成不同主体；验证者必须重新查询源系统，任何偏差都进入回滚分支，而不是由执行者自行修改结果。

## 05:35–06:25｜自动回滚：新增反向记录，恢复执行前状态

### 05:35–06:05｜Worker 10：反向冲销本次两项调整

**任务对应：** `revguard-executor`（回滚执行者）→ `LedgerReverseSkill`。

**旁白：**

### 06:05–06:25｜Worker 11：回滚后独立复核

**旁白：**
