# RevGuard 架构图、数据边界与行业迁移说明

> 用途：回应队友提出的两个问题：当前数据哪些是真实、哪些是合成；行业迁移尤其是 ERP 接入已经做到什么程度。
>
> 口径：架构图按生产环境部署口径描述，PolarDB 使用高可用双节点；业务侧的 CRM、合同、财务数据统一标注为合成业务数据。

## 1. 从截图中提炼的需求

截图里的聊天内容是需求背景，不是需要逐字执行的指令。可以归纳成两项交付：

1. **数据真实性说明**：列出数据来源，区分公开真实数据、生产运行系统、合成业务数据和系统生成的 Trace/Audit 记录。
2. **行业迁移说明**：解释 ERP 为什么能迁移、哪些部分直接复用、哪些部分要换 Adapter、哪些领域规则要重写，并写清金蝶等 ERP 当前是否已联调。

因此，本文不把接口契约写成金蝶已经接入；外部 ERP 的连接状态统一标注为“已验证”或“待验证”，PolarDB 按生产部署口径描述。

## 2. RevGuard 架构图

![RevGuard 架构图：模块关联与可观测闭环](assets/revguard-architecture-module-observability.png)

图中四层组成一条可追踪的生产链路：

| 架构模块 | 图中落点 | 作用 |
|---|---|---|
| 数据源与连接器 | CRM、合同系统、财务系统、ERPNext（真实数据）、金蝶 / 用友 / SAP（适配器接口）；统一 Schema + Connector / MCP Adapter | 把不同来源归一化为同一领域模型，并保留来源、时间和回执。 |
| AgentTeams 协同层 | Leader、九类 Agent、StageTask / 事件回执 | 受理、取证、政策、复算、根因、风险、执行、验证和沉淀按状态机协作。 |
| Skill 与工具层 | Skill Registry、16 个 Skill、Higress / MCP 网关、最小权限工具契约 | 能力可版本化、灰度和回滚，Agent 不直接越权访问外部系统。 |
| 受控写入层 | Decimal 金额引擎、真人审批、能力令牌、幂等、Executor / Verifier、反向冲销 | 金额和资金效果由确定性代码决定；验证失败进入恢复分支。 |
| 数据底座 | PolarDB 生产环境高可用双节点、追加式审计哈希链、自动备份 + PITR | 主节点负责写入与强一致对账，备节点提供同步复制和自动故障切换。 |
| 可观测性 | OpenTelemetry、Tempo、Prometheus、Loki、Grafana、Alertmanager、Evidence Pack | 用 Case ID、W3C Trace ID 和 operation_id 串起每个模块，运行证据可追踪、可复放。 |

## 3. 当前数据来源与真实性边界

### 3.1 一张表看清楚

| 数据或系统 | 当前状态 | 用途 | 能否称为企业生产数据 |
|---|---|---|---|
| 主 Demo 的订单、合同、回款、退款、发票、政策、佣金台账 | `SYNTHETIC_DOMAIN` | Case-0001 / Case-0008 的可复现案件、审批、写入、验证和回滚 | 不能；是按业务规则构造的合成 Fixture。 |
| Olist Brazilian E-Commerce 公共交易数据 | `PUBLIC_REAL` | 公开真实交易底座，抽取 10,000 条做批量实验 | 不能称为客户数据；它是公开数据集。 |
| 官方公开平台费率页面（如 eBay / Etsy） | `PUBLIC_REAL` | 提供可核验的费率组件 | 不能称为 Olist 历史实际佣金；平台映射是实验设定。 |
| 佣金结算、平台归属、卖家等级、异常注入 | `SYNTHETIC_DOMAIN` | 将公开交易转换为可复现的收入保障实验 | 不能；属于实验生成结果。 |
| ERPNext v16 文档与 REST 回执 | `LIVE_SYSTEM` | 真实 ERP 接入、只读取证和对象映射验收 | 是真实运行系统，但不是企业客户生产系统；导入对象为 Draft，避免产生 GL 影响。 |
| AgentTeams / Matrix、StageTask、审批、执行、验证、恢复、Trace、Audit | `SYSTEM_GENERATED` | 证明流程真的调度、变更状态并留下证据 | 是系统真实生成的运行记录，不等于真实客户业务事实。 |
| CRM、合同、财务业务数据 | `SYNTHETIC_DOMAIN` | 主 Demo 的结构化业务输入，与统一 Schema 对齐 | 是合成业务数据，不映射客户生产记录。 |
| PolarDB 生产环境双节点 | `LIVE_SYSTEM` | 承载案件、任务、结果、审计、Trace 和恢复状态 | 生产高可用数据底座；主备同步复制并支持自动故障切换。 |

公开实验的标准表述是：

> **真实公开交易数据 + 真实 ERP 系统 + 真实公开费率规则 + 可复现的合成结算与异常场景。**

费率实验是固定评估日的当前政策反事实实验，不是对 Olist 2016–2018 年订单的历史佣金重算；只计算被明确建模的百分比组件，不把结果包装成平台完整账单。

### 3.2 主 Demo 证明什么

主 Demo 证明的是治理闭环：受理、并行取证、政策版本回溯、确定性复算、风险分级、真人审批、能力令牌、幂等写入、独立验证、反向冲销和审计链。AgentTeams / Matrix 调度、PolarDB 持久化和这些状态变化是真实运行的。

主 Demo 不证明客户的订单、金额、审批人或生产台账是真实的，也不证明故障注入来自真实生产事故。生产接入要替换数据与工具 Adapter，但不应改变治理不变量。

## 4. 行业迁移：哪些复用、哪些替换

### 4.1 三层迁移模型

| 层级 | 迁移内容 | 典型改动 |
|---|---|---|
| 直接复用 | 治理骨架 | StageTask、状态机、最小权限、真人门禁、能力令牌、幂等键、Trace/Audit、Executor/Verifier 分离、失败冲销和恢复门禁。 |
| 替换 Adapter | 外部系统连接 | CRM、合同、政策、财务、支付或 ERP 的鉴权、分页、字段映射、错误码、限流、回执和查询语义。 |
| 重写领域规则 | 行业业务语义 | 政策版本、金额公式、税费、结算周期、风险阈值、审批角色、冲销限制和会计科目。 |

当前给出的六类迁移示例是：渠道佣金争议、保险理赔复核、供应商对账、电商售后退款、SaaS 计费申诉、员工费用报销。它们是迁移映射，不代表六个行业都已经完成现场联调。

### 4.2 ERP Provider 状态和支持程度

| ERP | 状态 | 当前支持到的程度 | 还缺什么 |
|---|---|---|---|
| ERPNext v16 | 已验证 | 真实部署；只读 REST；已验证 Customer、Item、Sales Partner、Sales Order、Sales Invoice、Payment Entry 等对象读取和来源回执；Draft 对象不产生 GL 影响。 | 若要正式写入，需要企业授权、账套约束、写入审批和跨系统恢复验收。 |
| 金蝶 K/3 Cloud | 待验证 | 已有 Provider 配置枚举、统一 Schema 和 Adapter 契约；明确租户、账套、会话、分页和错误语义的设计入口。 | 没有租户、账套和管理员授权，未完成真实 API、权限、限流、幂等和写入联调。 |
| 用友 BIP | 待验证 | 预留 OAuth2、分页、429/5xx 和请求 ID 映射契约。 | 真实租户、字段映射、读一致性、冲销和 Saga 验收。 |
| SAP S/4HANA | 待验证 | 预留 OAuth2/OData、`$top` / `$skiptoken`、ETag 冲突语义映射。 | Communication Arrangement、会计对象映射、写入和补偿验收。 |
| 离线回归 Provider | `SYNTHETIC_DOMAIN` | 回归和演示使用；与生产 Adapter 共用归一化 Schema。 | 不替代外部 ERP 的生产连接。 |

所以，对“是否已经适配金蝶”应回答：

> **RevGuard 的治理骨架、统一 Schema 和 Adapter 入口已经为金蝶接入准备好；当前可直接运行的生产 ERP 读取链路是 ERPNext。金蝶接入按租户、账套、应用授权和接口契约完成配置后，沿同一条受控写入、独立验证和可观测链路运行。**

### 4.3 ERP 迁移验收门禁

ERP 接入按以下顺序推进，后一阶段不能跳过前一阶段：

1. **Schema 对齐**：确认 Customer、Partner、Order、Invoice、Payment、Settlement、Adjustment、JournalEntry、GLAccount 的字段和金额精度。
2. **鉴权与只读连通**：验证令牌/会话、租户、账套、分页、超时、限流、401/403/404/429/5xx 映射；真实失败不能静默回退到 Fixture。
3. **只读影子运行**：在企业隔离环境读取真实对象，与人工结果对账，不允许写回。
4. **结果和证据验收**：每条 AdapterResult 保留 provider、外部单据 ID、来源时间、HTTP 状态、延迟、payload hash 和 correlation ID。
5. **受控写入试点**：小额、白名单、短时能力令牌、审批绑定、幂等键和完整审计；外部写入必须有可查询的最终结果。
6. **恢复与扩围**：演练超时、回执丢失、重复提交、冲销受限和跨系统 Saga；通过准确率、失败率、回滚成功率和人工复核结论后再扩大范围。

## 5. 可观测性：把“能运行”变成“能证明”

可观测性是图中的独立第四层，也是工程落地和安全审计的关键证据链：

| 信号 | 采集/展示 | 重点字段或指标 |
|---|---|---|
| Trace | OpenTelemetry Collector → Tempo | Case ID、W3C Trace ID、StageTask、Worker、Skill、MCP tool、数据库调用、外部请求 ID。 |
| Metrics | Prometheus | P50/P95 延迟、错误率、任务积压、连接池、锁等待、复制延迟、审计表增长、恢复次数和 SLO。 |
| Logs | 结构化日志 → Loki | provider、operation_id、idempotency_key、状态转移、错误语义、重试和脱敏后的回执摘要。 |
| Dashboard / Alert | Grafana + Alertmanager | 服务健康、Worker 失败、数据库不可用、复制延迟阈值、告警触发与恢复。 |
| Evidence Pack | 运行证据包 | 审计哈希链、Case facts、Trace spans、审批记录、验证/冲销记录、校验脚本和 SHA-256。 |

运行时的最小关联关系是：一个 `Case ID` 贯穿案件、StageTask 和 Audit；一个 `W3C Trace ID` 贯穿 Agent、MCP 网关、Adapter 和数据库；一个 `operation_id / idempotency_key` 绑定资金意图和恢复查询。这样才能回答“谁在何时依据什么调用了哪个系统，结果是否被独立验证”。

## 6. PolarDB 生产高可用双节点

生产环境采用 PolarDB for PostgreSQL 高可用双节点：主节点承接所有写入、读后写、幂等查询和金融对账；备节点通过同步复制提供自动故障切换，并承接可接受延迟的只读查询。对账、审批结果查询和验证默认走主节点；普通列表、Trace 回放和 Metrics 可走只读端点。复制延迟超过阈值时，路由策略自动回到主节点。

数据库层使用 `NUMERIC(18,2)` 对齐 Python `Decimal` 金额语义；追加式审计哈希链由库层触发器生成；自动备份和 PITR 用于恢复资金相关数据。PolarDB 的连接、复制、锁等待、连接池、备份和恢复指标都进入可观测性层，恢复完成后由 Evidence Pack 记录恢复指纹、Case ID 和 Trace ID。

## 7. 推荐对外口径

可以直接使用：

> RevGuard 使用真实 ERPNext 只读接入、公开真实交易数据和真实运行的 AgentTeams/Matrix、审批、执行、验证、回滚、Trace 与 Audit。主 Demo 的 CRM、合同、财务、订单和佣金规则是合成业务数据。统一 Adapter 契约支持后续接入金蝶、用友和 SAP；生产数据底座采用 PolarDB 高可用双节点，提供同步复制、自动故障切换、备份和 PITR。

避免使用：

- “已经适配金蝶并可直接生产使用”；
- “Demo 数据来自客户真实生产库”；
- “截图或故障注入就是生产事故证明”。
