# 0.5.10 编排阶段记录与案件状态一致性

所有构建、测试、浏览器操作与故障均在 10.10.10.202 Docker 中执行。测试使用独立 SQLite 文件和独立 PostgreSQL 容器；每个 PG 合约创建唯一数据库，连接池上限为 1，避免嵌套事务借用连接掩盖问题。现有演示案件不参与故障或重置。

## 已复现的问题

`reproduction.log` 在 0.5.9 上执行真实 MCP 流程：旧 Verifier 已生成持久 StageResult，暂停其返回；通过实际人工恢复 HTTP 入口恢复案件，让新编排运行至 CLOSED；再释放旧结果。旧流程在案件状态迁移被版本检查拦住前，已经覆盖了新验证记录的回执和 checked_at。复现断言失败，证明仅保护 Worker 入账与案件状态还不够。

## 修复

证据包、审批投影、草稿执行、验证记录通过 `commit_case_stage` 提交：先在同一数据库事务中锁定案件，检查录制批次、状态代次和案件修订号；再写入投影、阶段审计以及案件进度。事务提交后才更新调用者内存中的案件。任一参与写入失败，整阶段撤销；旧编排器不能先覆盖记录再报冲突。

MCP 编排与其 Matrix 子类共用该路径；同步参考编排器的对应投影也使用同一入口。Worker 的已提交结果可以继续保留，阶段失败不会伪造 Worker 失败。该修复不声称同步参考模式中之前发出的模拟审批工具效果与阶段投影同事务；生产人工审批已有独立的原子决策入口。

## 边界复核

编排器已无直接保存证据、审批、执行、验证投影的调用。资金效果仍由既有事务、操作 ID 和 Worker 领取身份保护；独立数据库复现使用合成账务。归档文件依录制批次保存，受现有运行租约与重新准备门禁约束；工具仅生成回复草稿。外部 ERP、云 HA/PITR、整台 202 主机不可用时的异地监控，以及企业真实收益均不是本次单机验收结论。
