# RevGuard WebUI 用户手册

RevGuard WebUI 是面向企业渠道佣金结算异常的案件处理工作台。本手册用于说明 WebUI 的页面结构、字段口径、案件处理流程及风险控制规则，适用于业务运营、财务结算、审计和研发人员。

> **数据与运行边界**：本项目使用合成业务数据；Agent 调度、证据采集、政策匹配、确定性计算、审批、模拟台账写入、独立验证、回滚和审计链路可实际运行。WebUI 当前不连接企业财务生产库，也不执行银行转账。

---

## 1. 运行说明

在项目的 `revguard/` 目录执行：

```bash
make demo-ui
```

打开：<http://127.0.0.1:9000/demo/>

WebUI 会加载案件列表和选中案件的只读仪表盘数据。案件处理动作通过 RevGuard API 触发，页面不会预置成功、失败或回滚结果。

### 1.1 演示数据说明

当前 Demo 中的订单、代理商、合同、政策、回款、退款、发票及佣金台账均为合成 Fixture。合成数据用于复现典型的佣金少记、多记、政策版本错误、证据不足、审批和验证失败场景，不代表任何企业的真实交易或制度。

WebUI 中的“模拟记账（入账）”表示写入演示用佣金台账；该动作不等同于付款指令、付款成功或代理商实际收款。

## 2. 业务模型与金额口径

### 2.1 业务对象之间的关系

代理商佣金异常通常涉及以下业务对象：

| 业务对象 | 含义 | 主要用途 |
|---|---|---|
| 订单 | 客户购买商品或服务形成的交易记录 | 提供订单金额、商品、状态和业务日期 |
| 回款 | 客户向企业支付的款项 | 判断回款是否完成，并计算回款佣金 |
| 合同 | 企业与代理商之间的约定 | 确定政策编号、等级口径和时间口径 |
| 政策 | 佣金比例、适用条件和生效期间 | 计算订单应得佣金 |
| 佣金台账 | 按佣金组件记录已入账金额的账本 | 与规则计算结果进行对账 |
| 案件 | 一次异常调查、审批和执行的完整容器 | 关联证据、计算、审批、执行、验证和审计记录 |

### 2.2 金额字段定义

| WebUI 字段 | 定义 | 是否表示本次实际付款 |
|---|---|---|
| **订单金额** | 订单交易总额，通常作为销售佣金等规则的计算基数 | 否 |
| **已入账金额** | 当前佣金台账中已经记录的佣金合计 | 否；表示历史已记账金额 |
| **预期佣金（正确）** | 按正确政策、代理商等级、回款条件和其他适用条件重新计算出的累计应有佣金 | 否；表示累计应得口径 |
| **本次审批金额** | 当前审批记录对应的佣金台账调整额度 | 否；表示授权调整范围 |
| **执行（组件）金额** | 对单个佣金组件实际执行的台账调整额 | 否；表示模拟台账变更 |
| **验证实际读取** | 独立验证者执行后重新从台账读取到的金额 | 否；表示执行后的台账结果 |

“代理商应该得到多少”需要区分两个时间口径：

- **累计应得佣金**：查看“预期佣金（正确）”；
- **本次应补记或扣回的佣金**：查看“计算账本”中的逐组件“差异”，以及审批和执行记录。

当前 WebUI 不提供直接银行付款能力，因此无法仅凭“预期佣金”“本次审批金额”或“已入账金额”确认代理商已经实际收到款项。

### 2.3 佣金计算公式

规则引擎按组件计算佣金，基本关系为：

```text
预期佣金总额 = 所有满足适用条件的佣金组件的应有金额之和

组件差异 = 组件应有金额 - 组件已入账金额

总差异 = 所有组件差异的有符号合计
```

差异方向定义如下：

| 差异 | 业务含义 | 典型处理 |
|---:|---|---|
| 正数 | 台账少记，代理商存在补发方向 | 增加对应佣金组件的台账金额 |
| 负数 | 台账多记，存在扣回方向 | 减少对应佣金组件的台账金额 |
| 0 | 台账与规则计算一致 | 不产生调整 |

佣金计算由确定性规则引擎完成，使用固定政策版本、业务事实和舍入规则生成可复现结果；语言模型不直接决定最终财务金额。

### 2.4 佣金组件

| 组件代码 | 页面名称 | 业务含义 | 常见计算基数 |
|---|---|---|---|
| `SALES_COMMISSION` | 销售佣金 | 根据代理商等级和订单完成情况计算的销售奖励 | 订单金额 |
| `COLLECTION_COMMISSION` | 回款佣金 | 根据回款是否完成及回款时效计算的奖励 | 回款金额 |
| `MONTHLY_INCENTIVE` | 月度激励 | 满足当月订单数等条件后产生的激励 | 订单金额或政策指定基数 |

同一订单可以同时适用多个佣金组件。“预期佣金”是这些适用组件的合计，不应只根据销售佣金一行判断总额。

### 2.5 总差异与审批额度

总差异保留正负号，审批额度按各组件差异的绝对值合计：

```text
审批总额度 = Σ |每个组件差异|
```

例如：

| 组件 | 应有金额 | 已入账金额 | 差异 |
|---|---:|---:|---:|
| 销售佣金 | 8,000 | 15,000 | -7,000 |
| 回款佣金 | 3,000 | 0 | +3,000 |
| 合计 | 11,000 | 15,000 | **-4,000** |

该案例的净差异为 `-4,000`，但实际需要执行两笔相反方向的动作：扣回 7,000、补记 3,000。因此审批总额度为 `10,000`，而不是净差异的绝对值 `4,000`。

## 3. WebUI 页面结构

页面由以下区域组成：

1. 顶部案件导航和运行状态；
2. 案件摘要；
3. 治理流水线；
4. 案件详情 Tabs；
5. 右侧安全状态栏；
6. 人工审批控制弹窗。

### 3.1 顶部导航

| 元素 | 含义 |
|---|---|
| 案件选择器 | 切换当前查看的案件，选项通常显示“案件 ID · 当前状态” |
| 风险等级 | 显示案件当前风险等级 `L0` 至 `L3` |
| `本地 MCP` | 当前案件通过本地 MCP 参考链路执行 |
| `AgentTeams 已连接` | 当前案件通过 AgentTeams/Matrix 协同执行 |
| `人工审批` | 页面包含人类审批控制边界 |
| `合成业务数据 · 真实运行链路` | 业务数据为合成数据，流程和 API 调用可实际运行 |
| `安全优先模式：已激活` | 权限、审批、幂等、验证和回滚约束已启用 |
| `重新准备` | 重置演示案件和演示台账；仅用于重新开始 Demo |
| 右侧状态 | 当前案件状态，不等同于页面连接状态 |

### 3.2 案件状态

| 状态 | 含义 | 处理建议 |
|---|---|---|
| `CREATED` | 案件已创建，尚未启动调查 | 启动多智能体调查 |
| `NORMALIZING` | 正在解析申诉内容和业务实体 | 等待任务完成 |
| `EVIDENCE_COLLECTING` | 正在收集跨系统证据 | 等待任务完成 |
| `WAITING_FOR_EVIDENCE` | 证据不足，或无法唯一定位业务对象 | 补充订单号、代理商或其他证据 |
| `POLICY_MATCHING` | 正在匹配业务时点政策 | 等待任务完成 |
| `CALCULATING` | 正在复算佣金 | 等待任务完成 |
| `ROOT_CAUSE_ANALYZING` | 正在分析少记、多记或漏记原因 | 等待任务完成 |
| `RISK_REVIEW` | 正在进行风险分级 | 等待任务完成 |
| `WAITING_FOR_APPROVAL` | 等待人类审批决定 | 核对后批准或驳回 |
| `READY_TO_EXECUTE` | 执行前置条件已满足 | 等待受控执行 |
| `EXECUTING` | 正在创建草稿或写入模拟台账 | 避免重复提交 |
| `VERIFYING` | 独立验证者正在复核执行结果 | 等待验证完成 |
| `RESOLVED` | 业务处理已形成结论 | 查看报告和审计记录 |
| `ROLLBACK_REQUIRED` | 验证发现偏差，进入冲销流程 | 确认回滚复核结果 |
| `ROLLED_BACK` | 已完成反向冲销并恢复安全基线 | 查看回滚证据 |
| `REJECTED` | 人工驳回，未继续执行 | 查看审批意见 |
| `CLOSED` | 案件已形成终态并关闭 | 结合执行记录判断关闭原因 |
| `FAILED` | 系统或阶段任务失败，未形成可靠终态 | 查看失败任务和错误信息 |

### 3.3 案件摘要

摘要区域用于快速确认主体、订单和金额关系。

| 字段 | 业务解释 |
|---|---|
| **代理商** | 佣金归属的渠道主体 |
| **订单号** | 被调查订单的业务主键 |
| **订单金额** | 订单交易总额 |
| **已入账金额** | 佣金台账已有金额 |
| **预期佣金（正确）** | 规则复算后的累计应有佣金 |
| **本次审批金额** | 当前审批记录或待处理调整额度 |
| **最终状态** | 案件当前最终处理状态 |
| **回滚后状态** | 回滚是否完成并通过独立复核；正常闭环时可能显示“不适用” |

推荐的阅读顺序为：先确认代理商和订单号，再对比已入账与预期佣金，随后进入“计算账本”查看逐组件差异，最后检查风险、执行和验证状态。

### 3.4 治理流水线

流水线展示案件从调查到安全闭环的阶段状态：

| 阶段 | 页面名称 | 阶段职责 |
|---:|---|---|
| 1 | **证据包** | 收集订单、等级、合同、回款、退款、发票、佣金台账和政策版本 |
| 2 | **政策** | 按合同约定的业务时间口径选择政策版本 |
| 3 | **计算预期佣金** | 使用确定性规则引擎计算各佣金组件 |
| 4 | **人工审批边界** | 根据风险、金额、证据和冲突决定审批路径 |
| 5 | **执行（组件）** | 按佣金组件创建草稿或写入模拟台账 |
| 6 | **独立验证（不同主体）** | 使用独立身份重新读取台账并核对结果 |
| 7 | **自动回滚** | 验证失败时新增反向冲销记录 |
| 8 | **回滚后状态** | 确认冲销后恢复至执行前台账基线 |

流水线下方的说明卡含义如下：

| 说明卡 | 含义 |
|---|---|
| 政策选择 | 展示已排除版本、最终采用版本及政策冲突 |
| 能力边界 | 展示总额度、当前金额、操作按钮和能力有效期 |
| 模拟记账（入账） | 展示已经写入模拟台账的组件和金额 |
| 佣金调整草稿 | 展示已生成但未写入台账的调整方案 |
| 验证结果 | 展示独立读取金额、差异和验证状态 |
| 自动回滚执行 | 展示已执行的反向冲销组件和金额 |
| 最终结果 | 展示正常闭环、回滚恢复、安全关闭或运行失败等结果 |

## 4. “决策依据” Tab

“决策依据”用于说明佣金结论的来源、计算过程、政策依据和 Agent 协作过程。

### 4.1 证据来源链

#### 表格列

| 列 | 含义 |
|---|---|
| 证据类型 | 证据对应的业务对象类别 |
| 来源系统 | 证据来源，例如 CRM、财务或合同系统 |
| 证据 ID | 来源系统的主键或引用编号 |
| 强度 | 证据可信程度；完整合成 Fixture 通常为 `STRONG` |
| 工具回执 | 本次查询的可追踪回执编号 |
| 校验 | 证据是否已采集并通过校验 |

#### 证据类型

| 类型 | 真实业务含义 |
|---|---|
| `ORDER` | 订单金额、商品、订单状态、创建日期、完成日期和销售负责人 |
| `TIER_HISTORY` | 代理商等级历史及每个等级的生效时间 |
| `CONTRACT` | 合同、政策编号、等级口径和时间口径 |
| `PAYMENT_RECORD` | 客户回款金额、回款状态和回款日期 |
| `REFUND_RECORD` | 退款、退货或取消订单记录 |
| `INVOICE` | 发票金额、发票状态和开票日期 |
| `COMMISSION_LEDGER` | 佣金组件、台账金额、政策版本和入账记录 |
| `POLICY_VERSIONS` | 政策历史版本、有效期、条款和规则定义 |

证据表中出现的金额不一定是代理商佣金。订单、发票和回款记录中的金额分别属于订单、发票和客户付款；佣金台账记录才直接用于核对代理商佣金。

### 4.2 计算账本

#### 表格列

| 列 | 含义 |
|---|---|
| 项目 | 佣金组件名称 |
| 公式 | 政策规定的计算公式 |
| 基数 | 公式实际使用的订单金额、回款金额等 |
| 比例 | 适用比例，例如 `15%` 或 `3%` |
| 计算 | 将业务事实代入公式后的可读表达式 |
| 应有金额 | 规则引擎计算出的组件金额 |
| 已发布 | 当前界面字段；业务上表示已发布/已入账金额 |
| 差异 | 应有金额减已入账金额，保留正负号 |

页面默认重点展示差异不为 0 的组件；金额一致的组件可能不单独显示，但合计仍包含所有适用组件。

#### 账本总数

| 总数 | 含义 |
|---|---|
| **应有** | 按正确政策计算出的佣金合计 |
| **已记** | 佣金台账已有金额合计 |
| **差额** | 应有减已记的有符号合计 |

### 4.3 政策时间线

政策时间线用于解释政策版本的选择结果。

| 页面元素 | 含义 |
|---|---|
| 政策版本节点 | 可被评估的历史政策版本 |
| 已选中 | 覆盖业务时点并最终用于计算的版本 |
| 未选中/已排除 | 因有效期或适用条件不满足而未采用的版本 |
| 业务日期 | 用于匹配政策的日期 |
| 等级 | 业务时点回溯得到的代理商等级 |
| 引用条款 | 支持政策和计算结论的条款编号 |

政策通常按合同约定的业务时间字段匹配，例如订单创建日期或回款完成日期，而不是简单使用当前日期或当前代理商等级。政策时间线会保留被排除版本和选择原因，便于复核。

### 4.4 多智能体协同任务账本

该板块记录各 Agent 的任务输入、输出、执行状态及关联标识，不代表额外的业务金额。

| 角色 | 主要职责 |
|---|---|
| 受理智能体 | 解析邮件或工单，识别案件、代理商和订单 |
| 取证智能体 | 只读查询跨系统证据 |
| 政策智能体 | 回溯业务时点并选择政策版本 |
| 计算智能体 | 调用确定性规则引擎计算佣金 |
| 风险智能体 | 进行风险分级并生成审批路由 |
| 执行智能体 | 创建草稿、写入或冲销模拟台账 |
| 验证智能体 | 使用独立只读身份重新查询并复核 |
| 回滚智能体 | 在验证失败时执行受控反向冲销 |

任务卡片常见字段：

| 字段 | 含义 |
|---|---|
| 任务输入 | 任务开始时保存的输入快照 |
| 任务输出 | 该阶段实际持久化的结构化结果 |
| 执行者 | 执行该任务的 Agent 或 Worker |
| 传输 | Matrix、本地 MCP 或 MCP 网关等通信方式 |
| 状态 | 待处理、执行中、已成功、失败待重试或最终失败 |
| 第 N 次 | 当前任务的执行尝试次数 |
| 任务/请求/房间/消息/回执/追踪 | 用于关联任务、通信、工具调用和 Trace 的标识 |

只有阶段结果成功持久化后，案件状态才允许推进。发生失败时，应优先查看对应任务的输入、输出、错误和关联 Trace。

## 5. “执行与审计” Tab

该 Tab 用于确认系统实际执行了哪些动作、由谁执行、耗时如何，以及失败是否被记录。

### 5.1 本次运行追踪耗时

| Trace 类型 | 含义 |
|---|---|
| `AGENT` | Agent 从接收任务到完成的端到端耗时，可能包含通信等待 |
| `SKILL` | API 进程内某个稳定能力的执行耗时 |
| `TOOL` | CRM、合同、财务或台账工具调用耗时 |
| `APPROVAL` | 人工身份验证和审批动作的追踪 |

执行者、耗时和状态用于定位性能或流程问题。Agent 端到端耗时与 Skill/Tool 进程内耗时的统计口径不同，不应直接混合比较。

### 5.2 不可篡改审计详情

审计详情以追加式事件链记录案件过程。常见事件如下：

| 事件 | 含义 |
|---|---|
| `CASE_CREATED` | 案件创建 |
| `EVIDENCE_COLLECTED` | 证据采集完成，记录证据完整度和缺口 |
| `POLICY_MATCHED` | 政策版本匹配完成 |
| `CALCULATED` | 确定性金额复算完成 |
| `RISK_CLASSIFIED` | 风险等级及执行限制确定 |
| `APPROVAL_DECIDED` | 人类批准或驳回，并记录审批身份 |
| `EXECUTED` | 某个佣金组件产生台账调整 |
| `VERIFIED` | 独立验证完成，结果可能通过或失败 |
| `ROLLED_BACK` | 某项已执行调整产生反向冲销 |
| `ROLLBACK_VERIFIED` | 回滚后的台账基线复核完成 |
| `TEAM_RUN_FAILED` | AgentTeams 运行阶段失败 |
| `KNOWLEDGE_ARCHIVED` | 案件结果归档为可复用样本 |

每条审计事件通常包含创建时间、执行者、事件名称及关联 ID。审计事件用于证明动作是否发生和由谁触发；具体金额应结合计算账本、执行记录和验证结果判断。

### 5.3 执行记录

执行记录按佣金组件保存以下信息：

- `action_id`：调整动作 ID；
- `action_type`：草稿、台账调整或其他动作类型；
- `amount`：该组件的有符号调整额；
- `before_snapshot`：执行前台账快照；
- `after_snapshot`：执行后台账快照；
- `idempotency_key`：防止同一动作重复写入的幂等键；
- `ledger_entry`：台账写入结果；
- `rollback_token_ref`：回滚能力的指纹引用。

回滚通过新增反向记录实现，不物理删除原台账记录，以保留完整审计链。

## 6. “权限边界” Tab

该 Tab 说明系统在当前案件中“最多允许执行什么”，不表示实际已经使用了多少资金。

### 6.1 审批与能力边界

| 字段 | 含义 |
|---|---|
| 案件绑定 | 当前审批和执行能力只能用于指定案件 |
| 币种 | 当前案件的金额币种，演示数据通常为 `KES` |
| 总额度上限 | 本次授权允许调整的最高总额 |
| 组件额度 | 销售佣金、回款佣金等各组件的独立调整上限 |
| 能力令牌有效期 | 受控执行能力的有效时间，当前 Demo 通常为 15 分钟 |
| 审批角色 | 需要完成审批的角色，例如财务负责人 |
| 人类审批人 | 实际完成身份验证和审批的主体 |
| Matrix 身份 | AgentTeams/Matrix 中绑定的人类身份 |
| 身份验证方式 | 本次审批使用的身份验证方式 |
| 动作证明指纹 | 人类对当前案件、审批单和动作的证明引用 |
| 能力指纹 | 审批后签发的受限执行能力引用 |

总额度和组件额度同时生效。总额未超限但某个组件超限，或组件均未超限但总额超限，均不得执行。

页面只展示令牌指纹，不展示审批令牌、回滚令牌或密码原文。指纹不能作为接口调用凭证。

### 6.2 四重约束

| 约束 | 含义 |
|---|---|
| 任务不漂移 | 状态、技能、执行者、输入快照和案件版本绑定 |
| 审批不自签 | Agent 不能替代审批人完成高风险审批 |
| 额度不外溢 | 总额度和逐组件额度共同限制调整范围 |
| 权限不升级 | 服务端身份、角色、权限范围和执行者白名单共同约束 |

### 6.3 安全回归证据

该区域展示已存档的确定性安全评测，例如伪造或过期令牌、跨案件调用、权限升级、组件额度、并发双写和回滚重放测试。

存档评测用于说明系统已覆盖的测试范围，不代表当前案件现场刚刚执行了同一组安全探针。

## 7. “价值模拟” Tab

页面主标题为“企业价值模拟器”。该 Tab 将合成案件的处理效率基线与可调整的业务量、人工成本组合，用于演示潜在的处理能力和预算空间，不参与佣金计算或审批。

### 7.1 输入参数

| 输入 | 含义 |
|---|---|
| 月均异常案件量 | 假设每月需要处理的异常案件数 |
| 综合人工成本 | 假设每小时人工处理成本 |
| 快速情景 | 预设的案件量，例如 100、500、1,000 案/月 |

### 7.2 指标

| 指标 | 含义 |
|---|---|
| 处理时长下降 | 合成样本中人工处理时长与 RevGuard 处理时长的中位数差异 |
| 同等工时理论吞吐 | 在相同人工时间内理论可处理的案件倍数 |
| 每月释放处理工时 | 每案节省时间乘以月案件量后的小时数 |
| 模拟人工经费空间 | 释放工时乘以人工成本；不是现金节省承诺 |
| 合成样本前后对照 | 单案处理时长、错付样本率和追回成本指数等对照指标 |

计算公式：

```text
每月释放处理工时 = 每案节省分钟 × 月案件量 ÷ 60

模拟人工经费空间 = 每月释放处理工时 × 综合人工成本
```

页面中的样本数和指标来自 `GOLDEN-001` 至 `GOLDEN-008` 等合成案件。接入企业真实数据后，应使用企业授权的脱敏基线重新计算。

## 10. 风险分级与执行路径

风险等级用于确定自动化边界，不用于表示佣金金额的正确性。

### 10.1 当前主要规则

| 等级 | 主要条件 | 系统处理 | 是否写入模拟台账 |
|---|---|---|---|
| **L0** | 只读诊断、金额为 0 或无差异 | 自动生成结论并关闭 | 否 |
| **L1** | 正向补发、金额不超过 5,000，且证据完整度不低于 0.9 | 自动生成不生效调整草稿 | 否 |
| **L2** | 未触发 L3 的一般有限调整；负向调整至少进入此级别 | 人工审批后受控执行 | 审批通过后可以 |
| **L3** | 金额超过 50,000、政策冲突、证据完整度过低或批量操作等 | 只生成处理方案，强制人工处理 | 否 |

当前实现中，以下情况会直接升级或限制自动执行：

- 调整金额超过 50,000；
- 存在未解决的政策冲突；
- 证据完整度低于 0.6；
- 涉及多笔订单或批量操作；
- 存在负向调整时，不能按 L1 草稿路径处理。

### 10.2 L1：草稿模式

L1 场景可自动生成调整草稿，但草稿不写入佣金台账，不触发写后验证，也不构成付款指令。案件关闭表示方案生成完成，不表示代理商已收到款项。

### 10.3 L2：审批后执行

L2 案件的处理顺序为：

```text
调查完成
  → 等待人工审批
  → 验证审批人身份
  → 批准或驳回
  → 批准：受控执行 → 独立验证
  → 驳回：REJECTED，不执行台账写入
```

审批通过后，系统仍会检查案件绑定、审批状态、能力有效期、币种、总额度、组件额度、幂等键、执行前快照和回滚能力。

### 10.4 L3：方案模式

L3 场景只生成调查结论和处理方案，不自动创建生效台账调整。后续由企业按照线下人工流程处理，当前 Demo 不代表该人工流程已经在系统内完成。

## 11. 人工审批操作

当案件处于 `WAITING_FOR_APPROVAL` 时，主操作按钮通常显示当前调整额度，例如“批准 14,400 KES”。

### 11.1 操作步骤

1. 确认案件 ID、代理商、订单号和风险等级；
2. 核对证据来源链、政策时间线和计算账本；
3. 确认逐组件差异、审批总额度和组件额度；
4. 选择“批准”或“驳回”；
5. 输入 AgentTeams/Matrix 审批账号和密码；
6. 执行审批账号身份验证；
7. 核对案件、审批单和动作绑定关系；
8. 填写审批意见并提交决定。

### 11.2 审批凭证说明

- 密码仅用于本次身份验证，Agent 无法读取；
- 身份证明绑定当前案件、审批单和动作；
- 批准后签发短时、限案件、限币种、限总额和限组件的执行能力；
- 驳回后不签发执行能力，也不继续写入台账；
- 页面展示的指纹是脱敏引用，不是原始凭证。

## 12. 标准案件处理流程

### 12.1 业务复核顺序

1. **主体确认**：确认代理商和订单号；
2. **证据确认**：确认订单、合同、回款、退款和佣金台账证据完整；
3. **政策确认**：确认政策按正确业务日期匹配，代理商等级按正确生效日期回溯；
4. **计算确认**：确认公式、基数、比例和佣金组件；
5. **差异确认**：确认每个正向补记和负向扣回差异均有解释；
6. **风险确认**：确认 L1、L2 或 L3 路径与案件金额及证据情况相符；
7. **结果确认**：写入后必须检查独立验证；验证失败时必须检查回滚复核。

### 12.2 金额关系与处理方式

| 金额关系 | 业务判断 | 后续处理 |
|---|---|---|
| 预期佣金 = 已入账金额 | 未发现佣金差异 | 无需调整，生成只读结论 |
| 预期佣金 > 已入账金额 | 存在少记，属于补发方向 | 查看组件差异，再按风险等级处理 |
| 预期佣金 < 已入账金额 | 存在多记，属于扣回方向 | 核对政策、等级和回款，通常需要人工审批 |
| 部分组件应有、台账为 0 | 组件漏记 | 确认适用条件后按组件补记 |
| 同时存在正负差异 | 多个组件方向不同 | 按组件执行，审批额度按绝对值合计 |
| 执行后实际读取不等于预期 | 执行结果不一致 | 触发回滚并复核安全基线 |
| 案件关闭但没有台账写入 | 草稿、风险拦截、驳回或只读结论 | 结合执行记录和审计事件判断关闭原因 |

## 13. 典型合成案例

### 13.1 少记佣金：L2 审批后补发

假设订单金额为 180,000 KES，订单时点代理商等级为 GOLD，佣金台账已记录销售佣金 18,000 KES：

```text
销售佣金：180,000 × 15% = 27,000，差异 +9,000
回款佣金：180,000 × 3%  =  5,400，差异 +5,400
累计应有佣金：32,400
累计已入账佣金：18,000
本次调整：+14,400
```

处理结果：案件进入 L2 → 人工审批 → 分别执行销售佣金 `+9,000` 和回款佣金 `+5,400` → 独立读取台账累计金额 `32,400` → 验证通过后正常关闭。

### 13.2 多记与漏记并存：按组件处理

假设销售佣金多记 7,000，回款佣金漏记 3,000：

```text
销售佣金调整：-7,000
回款佣金调整：+3,000
净差异：-4,000
审批总额度：10,000
```

处理时必须保留两笔组件动作，不能将其合并为单笔 `-4,000`，否则无法准确表达多记和漏记的原因，也会削弱额度控制和审计追踪。

### 13.3 小额补发：L1 草稿

假设应有佣金为 4,180 KES、已入账为 0，且证据完整、调整为正向补发：

- 系统生成佣金调整草稿；
- 草稿不写入模拟佣金台账；
- 页面可以形成安全关闭状态；
- 该状态不代表实际付款完成。

### 13.4 大额补发：L3 方案

假设订单金额为 400,000 KES，按正确政策计算出的预期佣金为 72,000 KES，已入账为 0：

```text
预期佣金：72,000 KES
已入账佣金：0 KES
待处理差异：+72,000 KES
```

由于调整金额超过 50,000 KES，该案件按当前规则进入 L3。系统生成处理方案并禁止自动写入模拟台账；后续处理需要遵循企业的人工高风险流程。

### 13.5 无差异：L0 只读结论

假设规则引擎计算出的佣金与佣金台账完全一致：

- 不创建佣金调整；
- 不创建人工审批；
- 不写入模拟台账；
- 案件形成“无需调整”的结论并关闭。

### 13.6 证据不足：等待补充信息

假设案件只包含代理商名称，没有订单号，且该代理商名下存在多笔候选订单：

- 案件进入 `WAITING_FOR_EVIDENCE`；
- 系统记录候选订单和证据缺口；
- 需要补充订单号或其他唯一定位信息；
- 在定位不确定前，不生成确定性佣金结论。

## 14. 独立验证与自动回滚

执行者返回写入成功，并不等于目标台账最终正确。网络重试、并发写入、外部系统异常或数据变化都可能造成执行结果偏差。

RevGuard 将执行与验证分为不同主体：

1. Executor 按审批和能力边界写入调整；
2. Verifier 使用独立只读身份重新查询佣金台账；
3. 系统按总额和组件分别比较预期与实际；
4. 验证通过，案件正常闭环；
5. 验证失败，对已提交调整新增反向冲销；
6. 冲销后再次独立查询，确认恢复到执行前台账基线。

验证重点字段：

| 字段 | 含义 |
|---|---|
| `expected_amount` | 预期台账金额 |
| `actual_amount` | 独立查询到的实际台账金额 |
| `variance` | 实际金额与预期金额之间的差异 |
| `component_checks` | 各佣金组件的逐项检查结果 |
| `rollback_required` | 是否需要执行回滚 |

例如预期金额为 32,400 KES，独立读取为 32,401 KES，即使差异只有 1 KES，也不能直接视为验证通过；系统应进入冲销和回滚后复核路径。

## 15. 常见问题

### 15.1 订单金额是否等于代理商应得佣金？

不是。订单金额是交易金额，通常只是佣金计算基数。

### 15.2 预期佣金是否等于本次应付款？

不一定。预期佣金表示订单累计应有佣金；本次应调整金额还需要扣除已经入账的佣金，并按组件和风险规则确定。

### 15.3 本次审批金额是否等于实际付款金额？

不是。本次审批金额是佣金台账调整授权额度。当前 Demo 不执行银行转账。

### 15.4 已入账金额是否等于代理商已经收到的钱？

不一定。已入账金额表示佣金台账已有记录；实际支付状态需要由企业付款系统确认。

### 15.5 为什么审批金额有时不等于净差异？

因为审批额度按各组件差异的绝对值合计，避免补记和扣回相互抵消后低估实际操作范围。

### 15.6 批准后是否表示案件处理完成？

不是。批准只表示人类授权，后续仍需受控执行和独立验证；验证失败时还会进入回滚流程。

### 15.7 案件显示 `CLOSED` 是否表示代理商已收到款项？

不是。`CLOSED` 只表示案件形成终态，可能对应正常验证、草稿模式、风险拦截、人工驳回等不同路径，需结合执行记录和审计事件判断。

## 16. 术语表

| 术语 | 定义 |
|---|---|
| 代理商 / Partner | 参与渠道销售并可能获得佣金的主体 |
| 佣金组件 / Component | 销售佣金、回款佣金或月度激励等具体佣金项目 |
| 佣金台账 / Ledger | 记录各订单各佣金组件已入账金额的账本 |
| 已入账 / Posted | 已写入佣金台账的记录状态 |
| 预期 / Expected | 按正确政策计算出的应有金额 |
| 差异 / Delta | 应有金额减已入账金额，保留正负方向 |
| 调整 / Adjustment | 修正台账时产生的补记或扣回动作 |
| 草稿 / Draft | 已形成处理方案但尚未写入台账 |
| 审批额度 / Quota | 人类授权允许调整的总额或组件额度 |
| 执行 / Execute | 将授权后的调整写入模拟佣金台账 |
| 独立验证 / Verifier | 使用不同于执行者的身份重新查询和核对结果 |
| 回滚 / Rollback | 通过新增反向记录恢复执行前台账基线 |
| 幂等 / Idempotency | 同一动作重复提交时不产生重复写入 |
| Trace | Agent、Skill、Tool 和审批动作的运行追踪 |
| Audit | 追加式、可追溯的案件事件记录 |
| L0-L3 | 从只读诊断到强制人工处理的风险和执行边界 |
| 合成数据 | 为演示和测试构造、且不代表真实企业交易的数据 |

## 附录 A：WebUI 字段与实现口径

| 页面字段 | 当前主要来源 | 说明 |
|---|---|---|
| 订单金额 | `case.calculation_result.facts_snapshot.order_amount` | 订单交易额，不是佣金 |
| 已入账金额 | `root_cause_report.total_posted`，缺失时回退到案件申诉实际金额 | 佣金台账已有金额 |
| 预期佣金（正确） | `root_cause_report.total_expected`，缺失时回退到计算结果总额 | 累计应有佣金 |
| 本次审批金额 | 正式审批存在时取 `approval.amount`，否则回退到总差额 | 未形成正式审批记录时可能只是待处理差额 |
| 模拟记账 | `executions` 中的非草稿记录 | 按佣金组件保存正负调整额 |
| 佣金调整草稿 | `executions` 中的 `DRAFT` 记录 | 不写入台账 |
| 验证实际读取 | 验证结果中的 `actual_amount` | 来自独立验证查询 |
| 回滚后状态 | 案件状态、回滚复核和执行记录综合判断 | 通过才表示恢复安全基线 |

调查阶段尚未形成正式审批对象时，WebUI 可能用总差额填充“本次审批金额”，并使用 `PENDING` 作为展示状态。判断审批是否真正创建、批准或执行时，应以案件状态、审批记录、执行记录和审计事件为准。

## 附录 B：真实企业接入前的口径确认

接入真实 CRM、合同、财务台账或付款系统前，应由业务和财务共同确认：

- “已入账”表示记账、应付还是已付款；
- “预期佣金”是订单累计应得还是当前结算周期应得；
- 本次审批额度按净差异还是按组件绝对额计算；
- 佣金组件、政策版本和适用条件是否与企业制度一致；
- L1/L2/L3 阈值是否需要按币种、组织或企业制度调整；
- 模拟台账调整与真实付款指令之间的接口边界。

在上述口径完成确认前，不应将 Demo 字段直接作为企业正式财务口径或付款依据。
